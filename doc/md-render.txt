*md-render.txt*   Rendered markdown in a Neovim buffer           *md-render*

Rendered markdown in the window, with one key back to the source. The plugin
shows a markdown file as the engine laid it out — headings, tables, diagrams,
images and highlighted code — in a read-only buffer, and swaps the file's own
buffer back on request. A managed window is always in one of two states:
rendered (R) or source (S).

The engine is a separate binary. The plugin never renders markdown itself; it
spawns `md-render` and paints the JSON it writes. See
|md-render-engine-resolution| for where the binary is looked for.

1. REQUIREMENTS                                       *md-render-requirements*

  - Neovim 0.10 or newer.
  - The `md-render` engine binary. It is shipped as a release asset; a source
    build needs Rust 1.92 or newer.
  - A terminal with `'termguicolors'` for image artwork in braille. Without
    it, images fall back to the ASCII encoding and everything else is
    unchanged.

==============================================================================
2. INSTALLATION                                       *md-render-installation*

Put the plugin on 'runtimepath' with any package manager, then give it an
engine. The engine is a separate download or build, not part of the plugin.

Prebuilt engine:~
Download the archive for your platform from
https://github.com/Moler1995/markdown-rs.nvim/releases, unpack it, and put the
binary at: >

  <stdpath('data')>/md-render/md-render        (POSIX)
  <stdpath('data')>/md-render/md-render.exe    (Windows)
<
`stdpath('data')` is `~/.local/share/nvim` on Linux and macOS and
`~/AppData/Local/nvim-data` on Windows.

Source build:~
From a checkout of this repository: >

  cargo build --release -p md-render
  mkdir -p bin
  cp target/release/md-render bin/md-render
<
PowerShell: >

  cargo build --release -p md-render
  New-Item -ItemType Directory -Force bin | Out-Null
  Copy-Item target/release/md-render.exe bin/md-render.exe
<
A copy in the repository's `bin/` is what a plugin on 'runtimepath' from that
checkout runs. Rebuild and copy after changing the engine.

lazy.nvim:~
>lua
  {
    'Moler1995/markdown-rs.nvim',
    event = { 'BufReadPre *.md', 'BufNewFile *.md' },
    build = 'cargo build --release -p md-render && mkdir -p bin '
      .. '&& cp target/release/md-render bin/md-render',
    config = function()
      require('md-render').setup({})
    end,
  }
<
vim.pack:~
>lua
  vim.pack.add({ 'https://github.com/Moler1995/markdown-rs.nvim' })
  require('md-render').setup({})
<
mini.deps:~
>lua
  MiniDeps.add({ source = 'Moler1995/markdown-rs.nvim' })
  require('md-render').setup({})
<
Without a build hook, download the engine as described above. The plugin does
not fetch anything at startup.

3. ENGINE RESOLUTION                              *md-render-engine-resolution*

The engine is resolved in this order:

  1. the `engine` option, used as given — authoritative;
  2. `md-render` on `$PATH`;
  3. `<plugin-root>/bin/md-render[.exe]` — a local build;
  4. `<stdpath('data')>/md-render/md-render[.exe]` — a downloaded release.

A configured `engine` that is missing or not executable is an error; the
plugin does not fall through to another location, because that would hide a
configuration mistake behind a different binary. The automatic steps are each
checked with `executable()`, so a file that exists but cannot run is skipped.

The repository's `bin/` is ahead of the data directory so that a fresh local
build is not shadowed by an older download. |:checkhealth| reports which step
matched, which is how a `PATH` shadow becomes visible.

==============================================================================
4. SETUP                                                  *md-render.setup()*

>lua
  require('md-render').setup({ })
<
Merges the given options over the defaults; every field is optional and the
merge is deep. The startup file already installs the autocmds and commands, so
`setup()` is needed only to change an option. Calling it more than once is
safe: the autocmds and buffer keymaps are installed once.

`setup()` and the startup file both attach the markdown buffer already in the
window, so a package manager that loads the plugin from `FileType` still shows
the first buffer rendered, without reopening it.

5. OPTIONS                                              *md-render-options*

Every top-level key in `config.defaults`, with its default. Set a keymap to
`false` to leave that key alone.

`engine` (default `nil`)~
  Path to the engine binary. `nil` or the empty string means "resolve it"; see
  |md-render-engine-resolution|. A set path must be executable.

`theme` (default `'catppuccin_mocha'`)~
  Theme passed to the engine as `--theme`. Determines the palette of the
  rendered view.

`filetypes` (default `{ 'markdown' }`)~
  Filetypes whose buffers open in R. A buffer not listed is left alone: no
  state, no autocmds, no keymaps.

`image_mode` (default `'auto'`)~
  How images are drawn: `'auto'` (`braille` with `'termguicolors'`, otherwise
  `ascii`), `'braille'`, `'quads'`, `'blocks'`, `'ascii'` or `'off'`. `'off'`
  shows every image as its alt text. See |md-render-images|.

`image_inline` (default `'auto'`)~
  What R shows for an inline image: `'auto'` (a card everywhere, with the
  picture painted over it where the terminal can draw), `'card'` (the compact
  three-row card alone) or `'art'` (the artwork `image_mode` selects).
  `image_mode = 'off'` outranks both `'auto'` and `'card'`. The preview popup is
  unaffected. See |md-render-inline|.

`image_inline_original_bytes` (default `2097152`)~
  The largest file painted inline as it is instead of downscaled first. A file
  at or below this size is sent to the terminal unchanged, at its own
  resolution; a larger one becomes the engine's thumbnail, about 640 pixels
  across — or the picture's own size, when it has fewer pixels than that to
  give — which is what keeps every settle cheap. Only a still PNG or JPEG is
  sent this way: an animation would play itself inline, and every other format
  is left to the engine, which decodes more than the terminal does. `0` always
  asks for the thumbnail. The 8 MiB the OSC 1337 transport carries is a hard
  cap on the option. The choice belongs to that transport: on Kitty a PNG is
  sent as its path whatever its size, and anything else is the engine's PNG
  encode. See |md-render-inline|.

`image_palette` (default `'auto'`)~
  Where cell colours come from: `'auto'` (`full` for one-colour cells,
  `adaptive` for two-colour cells), `'theme'`, `'adaptive'` or `'full'`.

`image_background` (default `'terminal'`)~
  What transparent pixels are composited against: `'terminal'` (leave them to
  the terminal), `'theme'` or an `'#rrggbb'` colour.

`image_dither` (default `'auto'`)~
  Whether quantisation is ordered-dithered: `'auto'`, `true` or `false`.

`image_min_rows` (default `0`)~
  Enlarge a small image to at least this many display rows. Zero never
  enlarges.

`image_sharpen` (default `false`)~
  Unsharp-mask an image that was reduced to fit the page.

`image_max_height` (default `20`)~
  The most display rows one inline image may occupy. `false` removes the cap.
  The preview popup has its own height and is not affected.

`image_animation` (default `true`)~
  Fetch an animated image's frames so |keymaps.frame_next| can step through
  them. `false` renders every image as its first frame.

`graphics` (default `'auto'`)~
  Whether the terminal draws image files itself, in the preview popup and
  inline, instead of leaving the artwork. `'auto'` uses the OSC 1337 protocol
  in WezTerm and iTerm2, and the Kitty graphics protocol in kitty and Ghostty;
  `'off'` never writes a graphics sequence. See |md-render-graphics|.

`keymaps` (default below)~
  Buffer-local maps for R, S and the preview popup. Every key is optional and
  may be `false`; see |md-render-keymaps| for what each one does.
>lua
  keymaps = {
    toggle = '<leader>mr',
    write = '<C-s>',
    preview = '<CR>',
    follow = 'gf',
    follow_tab = 'gF',
    open_image = 'gx',
    frame_next = '<C-n>',
    pause = '<Space>',
    zoom_in = '+',
    zoom_out = '-',
    scroll_left = '<C-h>',
    scroll_right = '<C-l>',
  }
<
`preview` (default below)~
  The popup's caps as fractions of the editor's size. The popup is sized to
  fit the block and only then clamped.
>lua
  preview = { max_width_pct = 0.9, max_height_pct = 0.9 }
<
`resize_debounce` (default `100`)~
  Milliseconds to coalesce resizes and edits before re-rendering. Toggles are
  applied immediately and are not delayed.

`settle_debounce` (default `15`)~
  Milliseconds to coalesce scrolling, resizing and cursor motion before an
  inline picture is painted over its card again. Every one of those events
  wipes the paint, and the card is what shows until the next one, so this is a
  flicker the reader sees: keep it short. Raise it on a terminal that struggles
  with the payloads, since each paint sends one — and where a block the window
  cuts is painted, each new slice is a thumbnail the engine has to produce.
  `0` paints on the next event-loop tick and still folds one burst of events
  into one paint.

6. COMMANDS                                            *md-render-commands*

                                                        *:MdRenderToggle*
:MdRenderToggle        Swap between R and S in the current window. The same
                        thing |keymaps.toggle| does.

                                                        *:MdRenderShow*
:MdRenderShow          Show R in the current window, whether or not it is
                        already showing.

                                                        *:MdRenderSource*
:MdRenderSource        Show the source buffer in the current window.

                                                        *md-render-edit*
:edit                  Reloads the document from disk, in R as in any other
                        buffer. It re-reads the source, not the rendered
                        view, and shows the result in R; the window stays in R
                        with the same rendered buffer. Unsaved source changes
                        refuse it with |E37|, and `:edit!` discards them.

                                                        *:MdRenderReset*
:MdRenderReset         Forget every cached render and every highlight group
                        made for a rendered style. Use it after changing the
                        engine or the theme by hand. It does not reload the
                        plugin; see |md-render-troubleshooting|.

7. KEYMAPS                                             *md-render-keymaps*

R is the rendered view, S the source. "Both" means the map is set in each.

|keymaps.toggle| (both, default `<leader>mr`)~
  Swap between R and S. In normal mode, crossing lands on the source line the
  display line came from.

|keymaps.write| (both, default `<C-s>`)~
  Write the source buffer, even from R.

|keymaps.follow| (both, default `gf`)~
  Follow the link under the cursor. See |md-render-links|. It shadows Vim's
  `gf` in a managed buffer and hands the key back to Vim when the cursor is
  not on a link.

|keymaps.follow_tab| (both, default `gF`)~
  Follow a file link in a new tab, leaving R where it is. A URL or an anchor
  still acts in place.

|keymaps.preview| (R, default `<CR>`)~
  Preview the table, mermaid fence or image under the cursor in a popup; press
  again to close. On an image, where the terminal cannot draw the file itself,
  the file is opened in the default application instead. See |md-render-preview|
  and |md-render-inline|.

|keymaps.open_image| (R, default `gx`)~
  Open the image under the cursor with the system's default application. It
  does the same on a terminal that can draw images; the transport is not
  consulted. Off an image the key goes back to Vim.

|keymaps.frame_next| (R and the popup, default `<C-n>`)~
  Show the next frame of the animated image under the cursor. In the popup it
  steps while playback is paused. A card has no frames, so the key keeps its
  ordinary meaning there.

|keymaps.pause| (popup, default `<Space>`)~
  Pause or resume an animation playing in the popup. Bound only while an
  animated image is showing.

|keymaps.zoom_in| (popup, default `+`)~
  Restore the largest layout of a diagram. See |md-render-preview|.

|keymaps.zoom_out| (popup, default `-`)~
  Re-lay a diagram out at the popup's inner width, or at the narrowest whole
  layout when that is still too wide.

|keymaps.scroll_left| (popup, default `<C-h>`)~
  Scroll the popup sideways by the horizontal step of 'mousescroll'.

|keymaps.scroll_right| (popup, default `<C-l>`)~
  The same to the right.

Insert-entry keys (R only, not configurable)~
  `i`, `a`, `I`, `A`, `o` and `O` cross to S with the cursor on the source
  line the display line came from, and then hand the key to Vim. They are the
  mode's escape hatch, not a convenience, which is why they are fixed.
  `Esc` is deliberately not one of them: leaving insert mode is Vim's
  business, and a view that came back on `Esc` could not be edited in.

8. LINKS                                                    *md-render-links*

`gf` and `gF` open what is under the cursor:

  - a file, resolved relative to the document holding the link; an absolute
    destination is used as given. `gF` opens it in a new tab;
  - a URL, through `vim.ui.open`;
  - an anchor — `#section` on its own or after a path — which scrolls to the
    heading it names.

In R the link is read from the source text: the display row is first mapped
back to the source line it came from, so the engine's output does not need to
carry link targets. A source line that holds more than one link is resolved by
the label under the cursor — the labels are matched, in order, against the text
of the rows that line produced, which survives wrapping. A label whose rendered
form differs from its source (inline markup inside the brackets) is not matched;
the first link on the line is used then.
A rendered mermaid diagram can carry links of its own — a
`click NODE href "..."` directive — and the node's label is underlined (the
`MdRenderLink` group) so it is visible. The hint follows the follow keys: with
both set to `false` there is nothing to follow and no underline.

Following a file leaves a real jumplist entry at the source line, so `<C-o>`
comes back to the document and renders it again. The plugin's own R↔S swaps do
not add jumplist entries.

When the cursor is not on a link the key goes back to Vim, so a path written
as plain text still opens the way `gf` always did.

9. BLOCK PREVIEW AND ZOOM                               *md-render-preview*

A diagram or table wider than the window is clipped: the columns the engine
drops are not in the rendered buffer, so scrolling sideways cannot recover
them. `<CR>` on a ` ```mermaid ` fence or a table re-renders that block at a
budget of its own in a popup:

  - a diagram is laid out at the engine's largest budget, so nothing is
    clipped;
  - a table is laid out at the popup's inner width floored at the window's,
    because a table wraps rather than clips.

`-` re-renders the diagram at the popup's inner width; if that is still
clipped, it re-renders at the narrowest layout the engine can produce whole and
adopts it only when it is whole and narrower. `+` restores the largest layout.
A spent key returns without spawning the engine. A cropped layout is never
shown. The title says the width a zoomed-out diagram is laid out at.

`<C-h>` and `<C-l>` scroll the popup sideways by the horizontal step of
'mousescroll' and can be held down. They work in a table's popup too, and do
nothing in an image's popup while the terminal is drawing the file.

`<CR>`, `q` and `Esc` close the popup; the window underneath is untouched. On
anything other than a diagram, table or image, `<CR>` keeps its ordinary
meaning.

10. IMAGES AND ANIMATION                                 *md-render-images*

A markdown image is drawn as a card: a box filled with the theme's raised
surface, with the file's name and the size its header reports on the middle
row. A card that no terminal paints the picture over is a compact placeholder,
three rows tall and as wide as the picture's box; a card the picture is painted
over takes the picture's box exactly, so the painting covers all of it. PNG,
JPEG, GIF, WebP, BMP, TIFF and ICO are supported. An image that cannot be
drawn — a URL, a missing file, an unsupported format, one over the engine's
limits — is shown as its alt text instead of a card, and nothing is reported: a
picture the reader cannot see is not an error in the document. Images inside a
table cell or a heading stay as alt text.

The card~
  The compact card is three rows for every image, whatever its shape — or as
  many rows as the page has, when it has fewer — so a document's placeholders
  line up. Its width is the picture's box, raised to whatever its hint needs
  and never wider than the window. Where a terminal paints the picture over the
  card, the card takes exactly the box the artwork would have had, column for
  column and row for row, and carries no caption: a picture may be transparent,
  and a transparent pixel would show the caption as letters inside the picture.

  Switching |image_inline| re-renders the document without reflowing it: only
  the picture's own rows change, and every one of them is attributed to the
  reference's source line as the artwork's rows were.

  The card carries a hint on its bottom row, a column in from its right edge:
  `<CR>/gx open image`, naming whichever of |keymaps.preview| and
  |keymaps.open_image| are bound — because neither a card nor an alt text says
  by itself that a key opens the picture. With both set to `false` there is no
  hint, and a compact card is then just the picture's box. The hint is virtual
  text: it is drawn over the row at
  the `MdRenderHint` group, which links to `Comment`, and never changes the
  line's own bytes, so the card stays exactly as wide as the engine drew it. An
  alt text — an image the engine cannot draw, and any image with |image_mode| =
  `'off'` — carries the hint after its last row instead. The character-cell
  artwork is left alone, and so is a card a terminal paints the picture over:
  the picture says enough, and text under it would be erased by the next
  placement.

Inline pictures                                          *md-render-inline*
  |image_inline| decides what happens to the card:

  - `'auto'` (default) keeps the card on every terminal and, where the
    terminal can draw (|md-render-graphics|), paints the picture over it.
  - `'card'` keeps the card and paints nothing, on any terminal.
  - `'art'` leaves the image to |image_mode|: the character-cell artwork, or
    alt text with `'off'`.

  A picture is painted over the rows of the block the window shows, and only
  once the viewport has been still for |settle_debounce| milliseconds — short
  on purpose, because until it paints the card is what the reader sees.
  Scrolling, resizing, a re-render and a cursor move all ask for that one
  repaint, so a wheel or a held key costs a burst one picture. A block the
  window cuts in half is painted up to the edge: the engine cuts the shown rows
  out of the whole block's picture, so what is on screen is the same picture at
  the same scale — continuing above and below the window — rather than the
  whole picture squeezed into the part that is left. The Kitty transport is
  handed the file itself and cannot crop, so there a block is painted only
  while it is wholly visible and keeps its card otherwise.

  A floating window over the block owns its cells, so the block keeps its card
  while one covers it, and gets its picture back when that window closes. This
  is what keeps the preview popup's own image on top: the terminal draws
  whatever was placed last, so a picture repainted under an open popup would
  cover it.

  A picture belongs to the tab page that shows its window. A window in another
  tab page is not painted at all: the screen position Neovim reports for it is
  the one it would have if it were showing, so painting from another tab would
  put this document's picture over the tab the reader had switched to. Entering
  a tab asks for the pictures of the windows it shows, since the cells they
  were painted on were off screen in the meantime.

  What is painted is the file itself while it is no larger than
  |image_inline_original_bytes| — at its own resolution, with no encode behind
  it — and otherwise a thumbnail of it about 640 pixels across, or at the
  picture's own size when that is smaller: a small picture that the engine
  enlarged would look soft where the file itself looks sharp, and which of the
  two a reader sees must not depend on how far the block is scrolled. A block
  the window cuts is always the engine's encode, whatever the file's size: a
  file's own bytes carry the whole picture, and the terminal cannot cut them.
  On the Kitty transport a PNG is sent as its path and the terminal reads the
  file itself; every other format is carried as the engine's PNG encode,
  because that transport names the picture's format in the sequence and
  decodes PNG alone.

  The paint is not the buffer's content. Every motion, search, yank and edit
  command acts on the card's text — an edit command cannot reach the file
  through a picture — and the picture returns when the scroll stops. A full
  redraw the plugin did not cause, `:redraw!` or `CTRL-L`, clears an OSC 1337
  picture until the next scroll; a Kitty placement survives the redraw and is
  deleted when its block leaves the window or R is left. A paint that fails —
  an unreadable file, a terminal that ignores the placement — leaves the card
  and says nothing.

  On an image, |keymaps.preview| opens the popup where the terminal can draw
  and otherwise opens the file in the default application, which is what
  |keymaps.open_image| does everywhere. The preview popup itself is not
  affected by |image_inline|. A card has no frames, so |keymaps.frame_next|
  keeps its ordinary meaning there.

Fitting~
  The image is fitted to the window's text width and height, and to
  |image_max_height| when that is smaller. It is never enlarged unless
  |image_min_rows| asks for it. Resizing the window redraws it at the new size.
  The preview popup is not capped by |image_max_height|.

Animation~
  An animated GIF or WebP is drawn on its first frame and does not play by
  itself. |keymaps.frame_next| advances it one frame, wrapping at the end, and
  goes back to Vim off an animated image. Frames are fetched the first time the
  key is pressed, so a document that is never stepped through never pays for
  decoding them. An animation over 256 frames is sampled down, keeping the
  loop's duration. One that would decode more than 4,096 frames or past the
  engine's pixel budget is refused, drawn on its first frame, and reported once
  when the step key is pressed. |image_animation| = `false` turns the frames
  off entirely.

  In the preview popup the image plays: each frame is shown for its own delay,
  with a 100 ms floor, and the loop repeats until the popup closes.
  |keymaps.pause| pauses and resumes; stepping works while paused.

Native drawing                                          *md-render-graphics*
  The preview popup can show the image file itself, drawn by the terminal at
  its own resolution, instead of the character-cell artwork. Nothing else
  changes: the popup is the same window at the same size and position, the
  artwork stays its content, and the popup's keys act as before except for
  scrolling, which does nothing while the image is shown. This needs Neovim
  0.12 or newer, whose `nvim_ui_send` writes the sequence, and a terminal the
  plugin can identify from the environment:

  - WezTerm and iTerm2 get the OSC 1337 inline-image protocol. The file is
    sent to the terminal, which draws it and plays an animated GIF, APNG or
    WebP itself, with the file's own delays and no timer in the editor.
  - kitty and Ghostty get the Kitty graphics protocol. The terminal reads the
    file from its path. That protocol cannot play a file, so an animated image
    keeps its character-art animation there; a still image is drawn natively.

  Where the terminal plays the file itself, the popup binds no playback key:
  |keymaps.pause| and |keymaps.frame_next| keep their ordinary meaning there,
  and the terminal's own controls are what stop or step the picture. Where the
  popup plays the character art — on Kitty, and wherever the file is not drawn
  natively — those keys work as described in Animation above.

  The file fills the popup's interior, stretched to the same cell box the
  artwork was laid out in, so its proportions can differ from the file's own by
  the terminal's cell shape. Nothing of the artwork is left showing at an edge.

  The same transport is what paints an inline picture over its card. There the
  OSC 1337 transport sends an encoded thumbnail in the block's cell box, and
  the Kitty transport sends a PNG's path or, for a file of any other format,
  the engine's PNG encode.

  `graphics = 'off'`, an unidentified terminal, a tmux or screen session, a
  URL or `data:` reference, or a file the plugin cannot read all leave the
  artwork visible and say nothing. An image over 8 MiB is not sent to the OSC
  transport; the Kitty transport sends a path, which has no such limit.

  The image is placed again after the editor is resized. A full redraw the
  plugin did not cause — `:redraw!` or `CTRL-L` — clears an OSC 1337 image
  until the next resize; a Kitty placement survives it. Closing the popup
  removes the image.

  Nothing moves the viewport while the image is shown — not the wheel, not the
  vertical scroll keys, not `<C-h>` and `<C-l>`: on the OSC transport an image
  is attached to the cells it covers, so the repaint any scroll causes removes
  it and leaves only the artwork. There is nothing to reach either way: an
  image is laid out to fit the popup, so no column or row lies past its edge.
  Every other key, including `gf`, search and yank, acts on the artwork as
  before.

`gx`~
  Opens the image's file with the operating system's default application.
  Relative destinations resolve against the document's directory. A remote
  URL, a `data:` URI or a missing file is reported, not fetched.

11. HEALTH                                                 *md-render-health*

`:checkhealth md-render` reports:

  - whether Neovim is new enough;
  - the resolved engine path and the step that matched;
  - the engine's `--version` output;
  - the wire format version from a minimal render, and whether this plugin
    understands it;
  - `'termguicolors'` and the image encoding it implies (a warning, not a
    failure);
  - which transport the preview popup draws images with, or which condition
    turned graphics off (a warning, not a failure);
  - what an inline image becomes — a card, a card with the picture painted
    over it, or the artwork — and why (a warning, not a failure);
  - the configured filetypes.

It runs the engine twice, with a timeout, and never renders the buffer you are
looking at. A failure names the value and the remedy.

12. TROUBLESHOOTING                              *md-render-troubleshooting*

Engine not found~
  `:checkhealth md-render` prints every location searched. Build the engine
  into the plugin's `bin/`, or download a release into
  `<stdpath('data')>/md-render/`. A configured `engine` path is authoritative,
  so an old path in your config wins over everything else.

Wire format mismatch~
  The message "speaks wire format N, but this plugin expects M" means the
  plugin and the engine are from different revisions. Rebuild the engine from
  the checkout (`cargo build --release -p md-render`) or upgrade both together.

No truecolor~
  Without `'termguicolors'`, images use the ASCII encoding. Enable it
  (`vim.o.termguicolors = true`) for braille artwork. Text, tables and
  diagrams are unaffected.

Lazy loading~
  Loading the plugin from `FileType` is supported: the buffer that triggered
  the event is attached and rendered without reopening it. If a buffer stays
  in S, check that its filetype is in |filetypes|.

Stale modules after an edit~
  Editing `lua/md-render/` while Neovim runs does not reload the module:
  restart Neovim. `:MdRenderReset` only clears cached renders and highlight
  groups, which is what to use after changing the engine binary or the
  colourscheme.
